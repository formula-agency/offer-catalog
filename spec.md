# Передача проекта: каталог офферов Формулы

Актуально на 5 ноября 2026 года, на основе опубликованного коммита `113780e`. Этот документ описывает наблюдаемое состояние кода и границы ответственности; планы и ТЗ обозначены отдельно. Начните с таблицы репозиториев, затем с раздела нужной вам части проекта.

## 1. Что где находится

| Часть | Репозиторий и ветка | Статус |

| Публичная витрина готовых рекламных баннеров | [`formula-agency/offer-catalog`](https://github.com/formula-agency/offer-catalog), `agent/publish-offer-catalog` | Источник [GitHub Pages](https://formula-agency.github.io/offer-catalog/). Статическая страница без серверного API. |

| Предкаталог, проверка офферов, очередь, сервер сотрудников | Закрытый [`digitalkindratlv-cell/catalog-formula`](https://github.com/digitalkindratlv-cell/catalog-formula), `main` и `agent/catalog-queue-integration` | Отдельное приложение. Доступ Леониду нужно выдать отдельно. Ветку интеграции не путать с `main`. |

В `formula-agency/offer-catalog` ветка `main` — старый стартовый коммит. Не переключайте Pages на неё. В локальном репозитории есть незакоммиченные пользовательские файлы: они не становятся частью передачи автоматически и не должны попадать в коммит «заодно» с документацией.

## 2. Публичная витрина: структура и поток данных

Технологии: HTML, CSS, JavaScript без фреймворка, PowerShell 7 для синхронизации, штатный Windows PowerShell для OCR. GitHub Pages отдаёт файлы ветки `agent/publish-offer-catalog` из корня. При открытии браузер читает `index.html`, `styles.css`, затем `offers-data.js` и `app.js`. Данные и изображения уже статические; браузер не получает токен Scout.

Основные файлы:

| Файл/папка | Роль |
| --- | --- |
| `index.html`, `styles.css`, `app.js` | Страница, фирменный UI, фильтры, карточки, модальное окно, скачивание готового изображения, отметка «Не актуально». |
| `Офферы Новостройки/`, `Офферы Новостройки 2/`, `Офферы Новостройки 3/`, `Рассрочка/` | Иерархия `тип / район / ЖК / Обработанные / файл`. В каталог входят только файлы внутри `Обработанные`. |
| `offers-data.js` | Генерируемый публичный снимок `window.OFFERS_CATALOG`; содержит `count`, даты и массив офферов. Не источник ручных правок. |
| `generate-offers-data.ps1` | Обходит папки, применяет нормализацию и метаданные, формирует `offers-data.js`. ID — первые 16 hex SHA-256 от пути (для первого набора — относительного пути, для остальных — с именем набора). Перемещение файла меняет ID. |
| `offer-metadata.json` | Подтверждённые метаданные по пути изображения: ссылка на квартиру, дополнительные категории и дата добавления при необходимости. |
| `catalog-exclusions.json` | Пути снятых с публикации офферов. Сами изображения при очистке не удаляются. |
| `extract-offer-areas.ps1`, `offer-area-cache.json`, `offer-area-overrides.json` | Извлечение площади и явные ручные исправления, когда источник подтверждён. |
| `sync-scout-data.ps1`, `scout-integration.ps1`, `scout-project-aliases.json`, `scout-manual-overrides.json`, `scout-data.json` | Сопоставление с Scout и публичная проекция цены/истории. История не доказывает актуальность рекламного условия. |
| `EDIT.MD` | Редакторский промпт для приведения сторонних баннеров к фирменному стилю. Это инструкция для подготовки изображения, не исполняемый конвейер. |
| `Обновить каталог.cmd` | OCR → синхронизация Scout → генерация данных. Требует локального доступа к Scout; не запускайте только ради проверки документации. |

Обычное добавление: получить исходный оффер и ссылку на лот → проверить условия и планировку → подготовить отдельный готовый баннер в фирменном стиле → положить его в соответствующую папку `Обработанные` → при необходимости прописать `sourceUrl`, дополнительный `types` и `addedAt` в `offer-metadata.json` → локально запустить обновление и проверить карточку → отдельно согласовать публикацию. Папка и имя файла являются частью структуры данных, а не только способом хранения.

`addedAt` берётся из явного metadata, затем из предыдущего `offers-data.js`, затем из даты первого появления пути в истории Git, а для нового незакоммиченного файла — из времени генерации. Метка `NEW` показывается семь суток; в опубликованной витрине есть и фильтр `NEW`. `types` допускает несколько категорий, их совместный выбор проверяется по **И** (`matchesSelectedTypes`). Это пересечение тегов **оффера**, а не проверка всех выбранных условий внутри **одного варианта покупки**. Последняя логика, единый блок акций и автоматический показ подходящего варианта описаны в ТЗ и остаются частью отдельной интеграции.

Отметка «Не актуально» хранится в `localStorage` конкретного браузера. Это не общий статус сотрудников и не запись в очередь. Кнопка «Скачать оффер» отдаёт готовый файл из `Обработанные`; код живой витрины не создаёт новый баннер и не пересчитывает его текст.

## 3. Как создаётся фирменный макет

В опубликованном каталоге нет воспроизводимого автоматического генератора баннеров. Исходный рекламный материал редактируется отдельно, а витрина публикует готовое изображение. Полный редакторский промпт и ограничения — `EDIT.MD`. Перед передачей нового макета проверяйте соответствие **каждого** результата своему исходнику: число изображений, геометрия и тип планировки, цены/платежи/ставки/сроки/площади, название ЖК и условия без домыслов. Не подменяйте чужим планом недостающий оригинал.

Цветовая система страницы задана переменными `:root` в `styles.css`: основной тёмно-фиолетовый `#271755`, дополнительный фиолетовый `#4c2b91`, оранжевый акцент `#ff6a16`, белые поверхности `#ffffff` и светлый фон `#f5f4f7`. Это ориентиры интерфейса, не разрешение менять исходные факты рекламного оффера. В баннере не добавлять логотип «Формула» или выдуманный ЖК, если их не было в исходнике/задании. Не переносить в готовое изображение элементы интерфейса скриншота.

Отдельно в закрытом предкаталоге есть **кодовый SVG-шаблон карточки**, а не редакторский промпт: `prototype/offer-catalog/card-template.js`. Он строит предпросмотр и скачиваемый PNG 2× по публичному контракту данных, с привязанной оригинальной планировкой/картинкой. См. `prototype/offer-catalog/README.md`, `catalog-types.d.ts`, `catalog-core.js` и тесты шаблона. Эти два способа создания материала не следует объединять без проверки источников и условий: живая витрина пока скачивает готовый файл, предкаталог умеет строить карточку из структурированных данных.

## 4. Предкаталог и очередь: отдельная система

Предкаталог хранит сохранённые офферы и все варианты покупки, позволяет сотрудникам разбирать предложения и отправлять выбранные ID в Google Sheets. Закрытый репозиторий уже содержит `AGENTS.md`, корневой `README.md`, `deploy/README.md`, `docs/catalog-filters-spec-final.md` и прототип в `prototype/offer-catalog/`. Для локального знакомства достаточно читать эти файлы; учётные данные не нужны. Для доступа к работающему серверу, таблице и материалам изображений требуются отдельные права.

ТЗ на целевую интеграцию — `catalog-filters-spec-final.md` (копия в предкаталоге: `docs/catalog-filters-spec-final.md`). Согласованное отображение: **одна карточка квартиры, автоматически выбранный подходящий вариант и переключатель остальных**. Все варианты остаются в одном оффере и не смешивают цену, ПВ, платёж и акции. Новая схема, нормализатор, фильтры и загрузчик находятся в ветке `agent/catalog-filters-spec` витрины; серверная версия очереди — в ветке `agent/catalog-queue-integration` предкаталога. Наличие этих веток само по себе не подтверждает рабочую сквозную загрузку или миграцию таблицы.

Ключевой путь целевой интеграции: сотрудник выбирает оффер в предкаталоге → отправщик собирает версионированный JSON по ID со всеми вариантами и ссылкой изображения → очередь Google Sheets → загрузчик сайта проверяет версию/изображение и делает upsert того же ID → обратный статус возвращается в очередь. Неизменённая версия пропускается; изменение в предкаталоге создаёт новую версию. Явный повтор загрузки отличается от обычной повторной отправки. Служебный токен и учётная запись Google остаются на сервере, не в JS/Pages.

До изменений рабочей таблицы, включения расписания или замены публичной ветки нужны отдельное разрешение, резервная копия, проверка синтетического импорта и план отката. Исторический импорт баннеров из папок и целевая очередь пока разные каналы, не смешивайте их записи по похожим названиям или цене.

## 5. Локальная проверка и выпуск

Для публичной витрины: `pwsh -File ./test-scout-integration.ps1` проверяет синтетические сценарии сопоставления Scout без рабочего API. Страница открывается как `index.html`; проверьте загрузку изображений, поиск, категории, мобильную ширину, модальное окно, прямую ссылку и скачивание фактического файла. Не запускайте `Обновить каталог.cmd`, если требуется только проверить UI: он обращается к Scout и перезаписывает генерируемые файлы.

Для ветки нового загрузчика инструкции тестов и синтетических данных находятся в её `README.md` и `docs/catalog-queue-implementation.md`. Для закрытого предкаталога — команды из его `README.md`. Проверки одной ветки не являются доказательством работоспособности другой и тем более сквозной связи с рабочей таблицей.

Перед выпуском: убедиться в нужной ветке → сохранить бэкап текущих данных/изображений → проверить `git status` и список staged-файлов → исключить ключи и рабочие отчёты → прогнать профильные тесты → проверить настольный и мобильный браузер → получить разрешение на изменение источника GitHub Pages → после выкладки проверить живой URL и возможность вернуться к предыдущему commit/ветке. Не публикуйте незакоммиченные локальные материалы только потому, что они находятся рядом с проектом.

## 6. Доступы и открытые вопросы для передачи

- Леониду нужен доступ к закрытому `digitalkindratlv-cell/catalog-formula`; публичная витрина доступна без приглашения. Доступ к серверу/таблице/Scout выдаётся владельцами отдельно, без передачи ключей в чат или Git.
- Фирменные исходники (логотипы, шрифты, PSD/Figma и т. п.) в действующем публичном репозитории не обнаружены. `EDIT.MD` и CSS фиксируют используемые правила, но не заменяют исходный дизайн-файл. Если такой файл существует вне репозитория, его нужно указать и передать отдельно.
- Код «сайта Формулы» как отдельного веб-проекта в доступных локальных репозиториях не подтверждён. Папка `formula` содержит CLI для формы обратного звонка, а не исходники корпоративного сайта; её не следует выдавать за сайт или публиковать вместе с каталогом.
- Нужно назначить ответственного за проверку актуальности условий, выпуск обработанных баннеров и решение о запуске очереди. Без этого наличие кода не гарантирует свежесть рекламы.
